# 运动台数据分析工具：MVP 架构重构方案

## 1. 重构背景与目标

当前工具在处理高频机电采样数据（如 dSPACE 或控制器录波）与频域 FRF 数据时，存在交互与计算逻辑高度耦合（Fat View）、界面响应易卡顿假死、以及基于 `handle` 类事件监听带来的内存泄漏风险。

本次重构的核心目标是：**从“脚本化思维”迈向“软件工程化思维”**。
通过引入 **MVP (Model-View-Presenter)** 架构和 MATLAB 现代 UI 引擎 (`uifigure` + `uigridlayout`)，实现严格的关注点分离，彻底消除 UI 线程阻塞与内存泄漏隐患，打造一个具备高可扩展性和高鲁棒性的工业级内部科研工具。

## 2. 核心架构设计 (MVP 层级)

系统按严格的“单向数据流”划分为四个相互解耦的层级。下层对上层一无所知，上层仅通过接口调用下层。

### 2.1 宿主与生命周期层 (Host Layer)

* **核心组件**: `SignalAnalysisApp`

* **核心职责**:

  * 作为程序唯一入口，创建主窗口 (`uifigure`) 和全局网格布局 (`uigridlayout`)。

  * 实例化各子模块的 View 和 Presenter，完成依赖注入（如将全局状态栏回调注入 Presenter）。

  * 接管全局生命周期（`CloseRequestFcn`），确保窗口关闭时显式销毁所有 Presenter 以释放内存。

### 2.2 视图层 (View Layer - 绝对的哑终端)

* **核心组件**: `TimeSeriesView`, `TransferFunctionView`

* **核心职责**:

  * 仅负责 UI 控件的装配、渲染与事件广播，内部全量使用 `uigridlayout` 实现自适应布局，摒弃绝对定位（`Position`）。

  * **零业务逻辑**：不包含任何诸如“采样率计算”、“环形缓冲”的逻辑，也不直接读取文件。

  * 暴露渲染接口供外部被动调用（如 `RenderWaveform`, `ShowLoading`, `ShowError`）。

  * 暴露交互事件供外部监听（如对外广播 `ImportButtonClicked`）。

### 2.3 控制与业务层 (Presenter Layer - 系统的大脑)

* **核心组件**: `TimeSeriesPresenter`, `TransferFunctionPresenter`

* **核心职责**:

  * 持有 View 和 Model 的句柄，桥接两端。

  * 监听 View 发出的用户交互事件，调度底层的 Service 进行重负载计算与文件 IO。

  * 将底层纯函数的计算结果更新至 Model，并调用 View 的接口进行界面刷新。

  * **异常收口**：全局的 `try...catch` 集中于此，捕获算法或解析错误后，通知 View 弹出友好的错误提示。

### 2.4 模型与服务层 (Model & Service Layer - 纯粹的科研基座)

* **模型组件**: `SessionData` (通道/数据集状态), `Dataset` (只读的数据载体)。

* **服务组件**: `ChannelOperations` (14 种纯函数数学运算), `DataReaderFactory` (纯函数数据解析 IO)。

* **核心职责**:

  * 绝对的无状态纯函数计算与数据承载，**完全不依赖任何 UI 组件**，可脱离系统在命令行独立调用及编写单元测试。

## 3. 物理目录结构设计

为保证模块解耦，工程必须按职责强制分包存储：

```
/MotionDataAnalyzer
  |-- StartApp.m               (启动脚本，仅负责实例化 SignalAnalysisApp)
  |-- /app                     (宿主层)
      |-- SignalAnalysisApp.m
  |-- /presenter               (控制层)
      |-- TimeSeriesPresenter.m
      |-- TransferFunctionPresenter.m
      |-- BasePresenter.m      (基类，提供统一的 Listener 内存清理机制)
  |-- /view                    (视图层)
      |-- TimeSeriesView.m
      |-- TransferFunctionView.m
  |-- /model                   (状态层)
      |-- SessionData.m
      |-- Dataset.m
  |-- /service                 (纯函数计算与IO核心，即原 core 目录)
      |-- ChannelOperations.m
      |-- DataReaderFactory.m
      |-- SignalProcessor.m
  |-- /tests                   (单元测试集)

```

## 4. 关键机制落地与排雷指南

针对 MATLAB 特有的底层机制，必须严格执行以下设计以防“踩坑”：

### 4.1 内存防漏机制 (Listener 生命周期管理)

* **痛点**: MATLAB 的 `addlistener` 极易产生驻留内存的僵尸对象。

* **落地**: 在 `BasePresenter` 或各 Presenter 中声明私有元胞数组 `Listeners = {}` 集中存储监听器句柄。重写 `delete` 方法，在应用关闭时（由 `SignalAnalysisApp` 触发）遍历并彻底 `delete` 所有监听器对象。

### 4.2 伪异步防假死机制 (UI 响应保障)

* **痛点**: `parfeval` 多线程会导致 MATLAB 内存翻倍拷贝数据（易引发 OOM），而同步读取 GB 级数据会导致界面“假死”。

* **落地**:

  1. 触发重负载任务时，Presenter 调用 View 显示阻断式加载动画 (`uiprogressdlg`)。

  2. 强制调用 `drawnow` 刷新渲染队列，激活转圈动画。

  3. 主线程同步执行 `DataReaderFactory.Import`（主线程阻塞但用户有明确视觉反馈）。

  4. 解析完毕后关闭弹窗，执行后续渲染。

### 4.3 大数据量渲染降级机制 (Grid 性能优化)

* **痛点**: 在 `uigridlayout` 中一次性循环渲染上百个独立的 UI 控件（如多通道的 `uicheckbox`）会导致严重的重绘卡顿。

* **落地**: 在时域分析器的通道选择模块，弃用零碎的复选框，改用单体 `uitable` 组件。第一列设为 `logical` 模拟复选效果，大幅度提升大通道数下的渲染与滚动性能。

## 5. 分阶段实施路线图

建议采用渐进式重构，切忌一蹴而就，每个阶段需确保单元测试闭环：

* **阶段 1：夯实纯粹的数据基座 (Service 层重构)**

  * 抽离所有业务逻辑到 `ChannelOperations` 和 `DataReaderFactory.ExtractFrfCurves`。

  * 确保纯函数无任何 UI 耦合，命令行传入 mock 矩阵单测通过。

* **阶段 2：搭建现代空壳 (App & View 层)**

  * 利用 `uifigure` 和 `uitabgroup` 编写全局入口与网格布局框架。

  * 静态组装 View 层的控件，验证界面自适应缩放无错位（此时按钮点击无反应）。

* **阶段 3：最小闭环验证 (FRF 传函分析器落地)**

  * 实现业务逻辑较简单的 `TransferFunctionPresenter`。

  * 跑通完整链路：点击导入 -> 调度 IO -> 获取纯净数据 -> 调用渲染接口更新三张 Bode/相关性子图。验证 Listener 的安全释放。

* **阶段 4：复杂状态攻坚 (时域分析器落地)**

  * 实现核心的 `TimeSeriesPresenter`。

  * 打通通道表格勾选 -> Presenter 捕获 -> 调用 `ChannelOperations` 数据切片 -> 更新波形图表的完整交互闭环。接入状态栏与自定义光标。
